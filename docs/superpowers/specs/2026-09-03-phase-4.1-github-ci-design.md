# Phase 4.1 — GitHub Actions CI Integration

**Status:** Design approved 2026-09-03
**Branch:** `feat/phase-4.1-github-ci`
**Depends on:** Phase 1 (run trigger + result, suite/environment model, BullMQ), Phase 2 (scope/group/team RBAC)

## Goal

Trigger a test-suite run on ShipItAnyway (SIA) from GitHub Actions CI, and publish the
pass/fail result back to GitHub as a commit status so a pull request can be gated on it.

Canonical scenario: PR raised → CI runs unit tests → CI triggers the E2E suite on SIA →
run completes → result posted back as a required commit status → PR becomes mergeable
(green) or blocked (red).

## Context discovered

- **No scoped API tokens exist yet.** Despite the roadmap's premise that Phase 2 delivers
  service-account tokens, only a single shared `WEBHOOK_SECRET` HMAC on the public
  `POST /webhooks/trigger` exists. All other auth is JWT-only (`req.jwtVerify()` in the
  `preHandler` at `backend/src/index.ts:112`). Phase 4.1 builds the real token layer.
- `RunTrigger` enum already has an unused `CI` value (`schema.prisma:262`).
- Scope resolution keys entirely off `userId`: `resolveScopes(userId, projectId)`,
  `requireScope(projectId, userId, scope)` (`utils/project-access.ts`). A token that maps to a
  user id reuses the entire authz machinery unchanged.
- The trigger unit in this product is **suite + environment** (mirrors `Schedule`, which has
  `suiteId? + testId? + environmentId?`). `Suite.testIds` is a JSON array of test ids.
- `fireSchedule` (`services/schedule-runner.ts`) already expands a suite→tests→runs,
  including data-driven batch handling and trigger tagging. It is coupled to a `Schedule` row
  and will be refactored so CI reuses the same expansion.
- BullMQ/Redis is already in the stack (Phase 1.2 scheduled runs), so delivery retry and a
  reconciliation sweep reuse existing infra.

## Design decisions (from brainstorming)

1. **Inbound auth (CI → SIA):** build scoped API tokens now. A token is an alternate
   credential for a headless service-account user; existing `requireScope` reused verbatim.
2. **Outbound (SIA → GitHub):** commit status via a per-project PAT (simplest;
   no GitHub App / Checks API in this phase).
3. **CI flow:** fire-and-forget + async commit status. The Actions job returns green as soon
   as it fires the trigger; the merge gate is the separate commit status marked a required
   check in branch protection.
4. **Trigger unit:** `suiteId` + `environmentId` (environment required for CI); `testId`
   single-check as optional fallback.
5. **Reliability:** every triggered check must reach a terminal commit status. Delivery retry
   (BullMQ), a reconciliation sweep for lost runs, and a superadmin manual resend. No PR
   hangs on a `pending` required check forever.

## Section 1 — Scoped API tokens (service-account credentials)

A token maps to a real headless `User`; token auth resolves `req.user` to that user id and
all downstream `requireScope(projectId, userId, scope)` calls are unchanged.

**Model:**
```prisma
model ApiToken {
  id         String    @id @default(cuid())
  name       String
  tokenHash  String    @unique      // sha256 of the raw token
  prefix     String                 // display only, e.g. "sia_ab12"
  userId     String
  user       User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  lastUsedAt DateTime?
  expiresAt  DateTime?
  revokedAt  DateTime?
  createdAt  DateTime  @default(now())
}
```
- `User` gains `isServiceAccount Boolean @default(false)`.
- Raw token (`sia_<random>`) shown **once** at creation, never stored.
- The service-account user is added to the target project's Team (membership) and a Group
  granting `runs_trigger` (+ `runs_read`), so its scopes flow through the existing
  group/team resolution. Read-only vs trigger = which group it is in (reused by 4.2 MCP).

**preHandler change (`index.ts`):** if `Authorization: Bearer sia_…` is present → sha256 →
look up `ApiToken` → reject if `revokedAt`/`expiresAt` passed → set
`req.user = { userId, email }` → bump `lastUsedAt` (best-effort). Otherwise fall back to the
existing `jwtVerify()` path. No change to any `requireScope` call site.

**Management route:** superadmin-only `/api-tokens` CRUD. Create returns the raw token once;
list shows prefix + `lastUsedAt`; delete = set `revokedAt`.

## Section 2 — Inbound trigger + run expansion

**Refactor:** extract the run-expansion core from `fireSchedule` into
```
createRunsForSelection({
  projectId, suiteId?, testId?, environmentId, trigger, ci?, scheduleId?
}) => { runIds, batchIds }
```
`fireSchedule` becomes a thin caller (`trigger:'SCHEDULE'`, `scheduleId`); the CI route is
another caller (`trigger:'CI'`, `ci`). The data-driven/batch handling is shared, not
duplicated.

**Endpoint:** `POST /ci/trigger` — authed by API token (not public).
```
{ suiteId, environmentId, ci: { repo, sha, ref?, prNumber?, runUrl?, correlationId } }
```
- `environmentId` **required** for CI.
- `projectId` derived from the suite; `requireScope(projectId, userId, 'runs_trigger')`.
- Creates runs via `createRunsForSelection` with `trigger:'CI'`, stamping CI fields +
  `ciCorrelationId` on every run.
- Creates `CiDelivery(PENDING)` and enqueues a `pending` status delivery job.
- Returns `202 { correlationId, runIds }`.

**`TestRun` CI link fields (all nullable):**
`ciRepo, ciSha, ciRef, ciPrNumber, ciRunUrl, ciCorrelationId`.

## Section 3 — Outbound GitHub client + status aggregation

**`services/github.ts`** — single responsibility:
`postCommitStatus({ repo, sha, state, targetUrl, description, context })` →
`POST /repos/{repo}/statuses/{sha}` with the project PAT.
- `state`: `pending | success | failure`.
- `context`: `shipitanyway/{slugified suite name}` — one stable value per suite, so it matches
  the required-check name in branch protection across re-runs. (A suite rename changes the
  context; documented caveat — re-set the required check if you rename.)
- `targetUrl`: the SIA run-result / batch page.

**PAT storage:** per-project GitHub config — `Project.ghRepo?` + a PAT stored encrypted the
same way environment secrets already are. Set by a holder of `project:manage`.

**Aggregation:** one CI trigger fans out to N tests across possibly several data-driven
batches, so status aggregates across **all runs sharing a `ciCorrelationId`**, not per batch.
On a run finishing with a `ciCorrelationId`, if any sibling with that id is still non-terminal,
do nothing; when all are terminal, compute aggregate (any failed → `failure`, else `success`)
and enqueue a terminal status delivery job. No new grouping model beyond the correlation id
(the `CiDelivery` row is the ledger).

**`github.sha` gotcha:** on `pull_request` events `github.sha` is the merge commit, not the PR
head. Commit status must be posted to `github.event.pull_request.head.sha` or the check will
not appear on the PR. The workflow template sends the head sha.

## Section 4 — CI status delivery (reliable, no eternal pending)

Two failure modes, both closed:
- **A. Run finished, GitHub POST failed** → delivery retry.
- **B. Run never reached terminal** (worker crash / lost run) → reconciliation.

**Model — delivery ledger, one row per trigger:**
```prisma
model CiDelivery {
  id            String        @id @default(cuid())
  correlationId String        @unique
  repo          String
  sha           String
  context       String
  prNumber      Int?
  state         CiDeliveryState @default(PENDING)  // PENDING | DELIVERED | FAILED
  attempts      Int           @default(0)
  lastError     String?
  lastAttemptAt DateTime?
  createdAt     DateTime      @default(now())
}
```

**Flow:**
1. `/ci/trigger` → `CiDelivery(PENDING)` → enqueue `pending` status delivery job.
2. Worker finish-hook: all runs for a `correlationId` terminal → compute aggregate → enqueue
   terminal status delivery job.
3. **Delivery job** (new BullMQ queue): POST commit status; success → `DELIVERED`; throw on
   failure → BullMQ native retry (`attempts: 5`, exponential backoff); exhausted → `FAILED`
   with `lastError`. This is "retry on recovery" for ~0 custom retry code.
4. **Reconciliation sweep** (BullMQ repeatable, ~5 min): runs with a `ciCorrelationId`
   non-terminal older than a timeout (~30 min) → mark `FAILED` → enqueue their delivery.
   Closes mode B.
5. **Superadmin manual resend:** `POST /ci/deliveries/:id/resend` → recompute aggregate from
   runs → enqueue delivery job. Escape hatch for `FAILED`/wedged deliveries.

**Guarantee:** every triggered check reaches a terminal commit status — via delivery retry,
reconciliation, or manual resend.

## Section 5 — Workflow template + frontend

**`.github/workflows/shipitanyway.yml`** (committed as a sample, not active CI):
```yaml
on: [push, pull_request]
jobs:
  ui-tests:
    runs-on: ubuntu-latest
    steps:
      - name: Trigger ShipItAnyway E2E suite
        run: |
          SHA="${{ github.event.pull_request.head.sha || github.sha }}"
          curl -fsS -X POST "$SIA_URL/ci/trigger" \
            -H "Authorization: Bearer $SIA_TOKEN" \
            -H "Content-Type: application/json" \
            -d "{\"suiteId\":\"$SIA_SUITE_ID\",\"environmentId\":\"$SIA_ENV_ID\",\"ci\":{\"repo\":\"${{ github.repository }}\",\"sha\":\"$SHA\",\"prNumber\":${{ github.event.number || 0 }},\"correlationId\":\"${{ github.run_id }}-${{ github.run_attempt }}\",\"runUrl\":\"${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}\"}}"
        env:
          SIA_URL: ${{ secrets.SIA_URL }}
          SIA_TOKEN: ${{ secrets.SIA_TOKEN }}
          SIA_SUITE_ID: ${{ vars.SIA_SUITE_ID }}
          SIA_ENV_ID: ${{ vars.SIA_ENV_ID }}
```
Merge gating: mark the `shipitanyway/*` status a required check in branch protection.

**Frontend:**
- Run-result page: CI badge (repo + short sha + PR link) when `ciSha` present.
- Superadmin CI deliveries list: state, sha, PR, `lastError`, with a **Resend** button on
  `FAILED` rows.

## Out of scope (YAGNI — deferrable to a later 4.1.x)

GitHub App + Checks API annotations, inbound GitHub webhooks, a CI-side polling endpoint,
a dedicated RunGroup model / group-level run UI, multi-PAT rotation.

## Affected areas

- **Data model:** `ApiToken`, `CiDelivery` + `CiDeliveryState`; `User.isServiceAccount`;
  `TestRun` CI fields; `Project.ghRepo` + PAT secret.
- **Auth & access:** token branch in `index.ts` preHandler; `/api-tokens` route.
- **API routes:** `/ci/trigger`, `/ci/deliveries/:id/resend`.
- **Execution:** `createRunsForSelection` refactor out of `schedule-runner.ts`; worker
  finish-hook; delivery queue + worker; reconciliation repeatable job.
- **New services:** `services/github.ts`.
- **Infra/CI:** `.github/workflows/shipitanyway.yml` sample.
- **Frontend:** run-result CI badge; superadmin CI deliveries view.
