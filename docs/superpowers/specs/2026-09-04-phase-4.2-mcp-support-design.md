# Phase 4.2 — MCP Support

**Status:** Design approved 2026-09-04
**Branch:** `feat/phase-4.2-mcp-support` (to be created)
**Depends on:** Phase 1 (run trigger + result, suite/environment model, BullMQ), Phase 2 (scope/group/team RBAC + `ApiToken`), Phase 4.1 (`createRunsForSelection`, scoped-token auth, `RunTrigger`)

## Goal

Expose ShipItAnyway (SIA) test runs, checks, and results to any external agent over MCP, so
an agent can query run history, read results, and trigger runs — with authority scoped to the
agent's own `sia_` token. The MCP server is reachable over **HTTP** (Streamable HTTP transport)
so remote agents and this repo's own tooling can reach it.

Canonical scenario: an agent connects to the SIA MCP server over HTTP with a scoped token →
lists projects it can see → triggers a suite run → receives a durable task handle → polls until
the run finishes → reads the pass/fail result and trace link. This same flow is the feature's
acceptance gate (dogfood): SIA is tested *through* its own MCP server.

## Target protocol

- **MCP revision `2026-07-28`** (current; date-versioned — there is no "MCP 2.0").
- **Transport:** Streamable HTTP. This revision uses a **stateless, per-request** model —
  protocol version and client capabilities travel in the message body under
  `_meta.io.modelcontextprotocol/*`; HTTP headers only mirror them for intermediaries. The
  legacy connection-scoped `initialize` handshake + server-initiated requests are back-compat
  only.
- **Tasks extension** (`io.modelcontextprotocol/tasks`): used for the long-running trigger flow
  (durable `taskId`, `tasks/get` polling, crash-resilient).

## Context discovered

- **An MCP server package already exists** — `mcp-server/` (`@shipitanyway/mcp-server`,
  `shipitanyway-recorder` v0.1.0) — but scoped to *recording / test authoring* (record, observe,
  click, save_test, list_tests, …) over **stdio**. Phase 4.2 is a distinct capability
  (query runs + trigger + results) and shifts the transport to HTTP.
- Reusable pattern in place: `buildTools(client)` → `ToolRecord` map, Zod `toolSchemas`,
  registered in a loop via `server.registerTool`; tools unit-tested without the SDK
  (`mcp-server/tests/tools.test.ts`).
- `mcp-server/src/client.ts` is a thin `fetch` wrapper (`BACKEND_URL` + single `BACKEND_TOKEN`
  Bearer) with an explicit ponytail comment: *"single configured service token; swap for a
  Phase-2 scoped project token."* This is the upgrade path.
- **Auth reuse:** SIA's global `preHandler` (`backend/src/index.ts`) already accepts a
  `sia_` Bearer token interchangeably with JWT — `resolveApiToken` → `req.user = { userId }`.
  `ApiToken` has **no per-token scope column**; a token inherits exactly its user's group scopes
  (`resolveUserScopes` → membership ∪ global). Read-only vs trigger = which group the token's
  user is in (VIEWER vs EDITOR). No model change needed.
- **Run/read/trigger already exists and is scoped:** `GET /runs/:id`, `GET /run-batches/:id`,
  `GET /tests/:id/runs` (scope `runs_read`); `GET /projects/:id/tests`, `GET /tests/:id`
  (`checks_read`); `POST /tests/:id/run` (`runs_trigger`); `createRunsForSelection`
  (`services/run-selection.ts`) is the single choke point every trigger path routes through.
- Only per-check run history exists; there is **no project-wide run listing** endpoint.
- `RunTrigger` enum values today: `Manual`, `Schedule`, `CI` — no `MCP`.
- `mcp-server` compose service already exists (`docker-compose.override.yml`) but as an idle
  stdio service (`stdin_open`, `tty:false`, `BACKEND_TOKEN`); no published port.
- Repo `.mcp.json` exists for Claude Code dev tooling (unrelated to the product server).

## Design decisions (from brainstorming)

1. **Server topology:** one product MCP server. Rename `mcp-server` from `shipitanyway-recorder`
   → `shipitanyway`; group tools by capability (authoring / reporting / execution). Registration
   is **gated at connect** by the token's scopes so an agent only sees tools it can use.
2. **Read surface:** add a project-wide run listing (`GET /projects/:id/runs`, scoped `runs_read`,
   filter + paginate) + a `list_runs` tool, so reporting agents can survey without walking
   check-by-check.
3. **Trigger:** new `POST /mcp/trigger` (scope `runs_trigger`) taking `testId` **or** `suiteId`
   + `environmentId`, routing through `createRunsForSelection` with a new `RunTrigger.MCP` value.
   Distinct provenance from Manual/CI. Not `/ci/trigger` (CI metadata is semantically wrong for
   agent runs).
4. **Transport:** Streamable HTTP, revision `2026-07-28`, stateless per-request. `Origin`
   validation on every connection (MUST). Drop stdio for the product server.
5. **Async trigger via Tasks:** `trigger_run` returns a `CreateTaskResult`; `taskId` maps to the
   run/batch; terminal state resolves to the run result. Falls back to a synchronous result if
   the client does not advertise the Tasks extension.
6. **Auth (pragmatic, no passthrough):** per-connection scoped `sia_` token (each agent supplies
   its own). The MCP server validates the token at connect and uses it for that session's backend
   calls. MCP server and backend are treated as **one SIA trust domain / one OAuth resource**, so
   the token's audience is SIA and forwarding within that boundary is not third-party token
   passthrough. Full OAuth 2.1 authorization-server compliance (RFC 9728 metadata, RFC 8707
   resource indicators, `WWW-Authenticate` scope challenges, PKCE, step-up) is **deferred** and
   documented as a known gap. The prior single-shared-`BACKEND_TOKEN` model (which erased the
   user) is removed.
7. **Dogfood verification:** MCP stays additive (UI trigger path untouched), but this feature's
   acceptance gate drives SIA end-to-end through the HTTP MCP server, and the product server is
   wired into the repo `.mcp.json` so this session / agents test SIA via it.

## Section 1 — One product MCP server (topology + transport)

Rename the package's server identity `shipitanyway-recorder` → `shipitanyway`. Keep the existing
`buildTools`/`ToolRecord`/Zod pattern. Tools grouped by capability:

- **authoring** (existing): `start_recording`, `observe`, `navigate`, `click`, `type`, `select`,
  `upload`, `assert`, `finish_recording`, `save_test`, `validate_test`, `list_tests`, `get_test`,
  `delete_test`.
- **reporting** (new): `list_projects`, `list_runs`, `get_run`, `get_run_batch`.
- **execution** (new): `trigger_run`.

Server runs a single long-running HTTP process using the SDK's Streamable HTTP server transport,
one MCP endpoint at `POST/GET /mcp`, plus `GET /health`. Listens on `MCP_PORT` (default 3100).

**Compliance guards (MUST/SHOULD):**
- Validate the `Origin` header on every incoming connection (DNS-rebinding). Allow-list from
  `MCP_ALLOWED_ORIGINS` (default localhost only).
- Bind localhost when running locally; container binds its own interface behind compose.
- Per-request capability + protocol-version negotiation via body `_meta` (SDK-handled).
- Return `400` on unsupported protocol version; standard session/`404` handling per SDK.

**SDK-version risk (verification item, not assumption):** repo pins
`@modelcontextprotocol/sdk ^1.30.0`. Before implementation, confirm the installed SDK implements
revision `2026-07-28` (stateless `_meta` negotiation) and the Tasks extension; upgrade the SDK if
not. This is the first task in the plan and blocks the transport + Tasks sections.

## Section 2 — Auth (per-connection scoped token, no passthrough)

Each MCP client connection MUST send `Authorization: Bearer sia_...` — its own scoped token.
The server:

1. Extracts the bearer from the incoming HTTP request; rejects missing/malformed with `401`
   before establishing the session. Never logs the token; never echoes it in errors.
2. Validates the token by calling the backend capabilities endpoint (Section 4) with it. A `401`
   from the backend → reject the connection `401`.
3. Binds a per-session `client` to that exact token; all backend calls for that session use it.
   Sessions are keyed by MCP session id; the token lives in session memory only.
4. Uses the returned scope union to gate which tool groups are registered for that session
   (Section 5). Per-project enforcement still happens server-side at each backend endpoint —
   gating is UX, not the security boundary.

No `ApiToken` model change. Trust-domain rationale (documented in the module and this spec):
the `sia_` token is a first-party SIA credential whose audience is SIA; the MCP server and the
SIA backend are one resource within that boundary, so session-scoped forwarding is not the
third-party token passthrough the MCP spec forbids. Full OAuth 2.1 resource-server behavior is a
future Phase 4.3 item.

## Section 3 — Backend: project-wide run listing

New route `GET /projects/:projectId/runs` — `requireScope(projectId, userId, 'runs_read')`.

- Query params: `status?` (RunStatus), `trigger?` (RunTrigger), `since?` (ISO datetime),
  `testId?`, `limit` (default 50, max 200), `cursor?` (opaque, `createdAt`+`id` keyset).
- Returns run summaries — `id`, `testId`, `test.name`, `status`, `trigger`, `startedAt`,
  `finishedAt`, `durationMs`, `environmentId`, `batchId`, and CI fields when present — plus
  `nextCursor`.
- Ordered `createdAt desc`. Keyset pagination (no offset scans).

Reuses existing Prisma access patterns; no new model.

## Section 4 — Backend: MCP trigger + capabilities endpoints

**`POST /mcp/trigger`** — `requireScope(projectId, userId, 'runs_trigger')`.
- Body: exactly one of `testId` | `suiteId`, plus `environmentId` (required). Reject both/neither
  `400`.
- `projectId` derived from the test/suite; scope checked against it.
- Routes through `createRunsForSelection({ testId?/suiteId?, environmentId, trigger: 'MCP' })`.
- Returns `202 { runIds, batchIds }`. `422` if a suite has no checks (mirrors `/ci/trigger`).

**`RunTrigger.MCP`** — new enum value + Prisma migration. Additive; existing rows unaffected.

**`GET /me/capabilities`** — authenticated (token or JWT), not project-scoped.
- Returns `{ userId, email, isSuperadmin, scopes: string[] }` where `scopes` is the api-format
  union of the caller's group scopes (`membershipScopes ∪ globalScopes`, via `toApiScope`).
- Answers "does this token ever hold scope X" for tool gating, and doubles as the MCP server's
  token-validation call (a `401` means invalid/expired/revoked token).

All three are wired into the global auth `preHandler` (non-public), so `sia_` tokens and JWT both
work unchanged.

## Section 5 — MCP client + tools

`mcp-server/src/client.ts`: add `getCapabilities()`, `listProjects()`,
`listRuns(projectId, filters)`, `getRun(id)`, `getRunBatch(id)`, `triggerRun(body)`. Each is a
thin `fetch` to the scoped endpoint using the session's token. Backend `401/403/404/422` surface
as MCP tool errors — no swallowing, no fallback masking.

New tool modules mirror the recorder pattern:
- `list_projects` → `GET /projects` (accessible projects).
- `list_runs(projectId, {status?, trigger?, since?, testId?, limit?, cursor?})` →
  `GET /projects/:id/runs`.
- `get_run(id)` → `GET /runs/:id` (includes trace metadata).
- `get_run_batch(id)` → `GET /run-batches/:id`.
- `trigger_run({testId?|suiteId, environmentId})` → `POST /mcp/trigger`, then models the run as a
  **Task** (Section 6).

**Tool gating** (per session, from `getCapabilities().scopes`):
- reporting tools registered if the token holds any `runs_read` or `checks_read`.
- execution tools if it holds `runs_trigger`.
- authoring tools if it holds `checks_edit`.

## Section 6 — Async trigger via the Tasks extension

Server advertises `io.modelcontextprotocol/tasks` in its `server/discover` capabilities. When a
client advertises the extension per-request, `trigger_run`:

1. Fires `POST /mcp/trigger`, gets `runIds`/`batchIds`.
2. Returns `CreateTaskResult` (`resultType: "task"`) with a `taskId` encoding the run/batch id(s),
   initial `status: working`, a `ttlMs`, and a `pollIntervalMs`.
3. `tasks/get` maps the SIA run/batch status → task status: SIA running → `working`; all runs
   terminal & passed → `completed` with `result` = the run result summary + trace links; any
   failed → `completed` with a result reporting the failure (or `failed` if the trigger itself
   errored). `tasks/cancel` is accepted and acknowledged (cooperative; SIA run cancellation is
   best-effort).

If the client does **not** advertise Tasks, `trigger_run` returns the `202` summary synchronously
and the agent uses `get_run`/`list_runs` to poll manually. Both paths hit the same backend.

The taskId is a durable handle over the backend run rows — no new server-side task store; task
state is derived from `TestRun`/`TestRunBatch` on each `tasks/get`.

## Section 7 — Infra + dogfood wiring

**`docker-compose.override.yml` `mcp-server`:** becomes a published HTTP service —
`restart: unless-stopped`, `ports ${MCP_HOST_PORT:-3100}:3100`, `depends_on: backend (healthy)`,
healthcheck `GET /health`, env `BACKEND_URL=http://backend:3000`, `MCP_PORT=3100`,
`MCP_ALLOWED_ORIGINS`. Remove `stdin_open`/`tty`; per-connection tokens replace `BACKEND_TOKEN`.
Dockerfile CMD runs the HTTP server.

**Repo `.mcp.json`:** add the product server so this session / agents test SIA through it:
```json
"shipitanyway": {
  "type": "http",
  "url": "http://localhost:3100/mcp",
  "headers": { "Authorization": "Bearer ${SIA_MCP_TOKEN}" }
}
```

## Section 8 — Testing

**Backend (unit, one file per tsx process — Redis-hang gotcha):**
- `GET /projects/:id/runs`: filters, keyset pagination, `runs_read` 403.
- `POST /mcp/trigger`: `testId` vs `suiteId` (400 on both/neither), missing `environmentId`,
  empty suite `422`, `runs_trigger` 403, `trigger=MCP` persisted.
- `GET /me/capabilities`: scope union (membership ∪ global), superadmin, `401` on
  revoked/expired token.

**MCP server (tools, no live SDK — existing `tools.test.ts` pattern, mock client):**
- Per-connection token: `401` on missing/malformed bearer.
- Gating: scope set → correct tool groups registered.
- Each tool calls the right endpoint with the session token; backend error codes surface as tool
  errors.
- Tasks: `trigger_run` returns a task when the extension is advertised, sync result when not;
  `tasks/get` maps run status → task status correctly (working / completed-pass /
  completed-fail).
- `Origin` allow-list: disallowed origin rejected.

**Acceptance (dogfood — the done-gate, replaces curl):**
Bring up compose → mint a scoped `sia_` token → connect to the HTTP MCP server →
`list_projects` → `trigger_run` → poll the returned task to terminal → `get_run` shows the
result. Green = feature done.

## Out of scope (YAGNI)

- **Full OAuth 2.1 authorization server** (RFC 9728/8707/9207, PKCE, DCR / Client-ID-Metadata,
  step-up scope challenges) — deferred to a Phase 4.3; documented gap.
- **Per-token scope column** on `ApiToken` — group membership already scopes tokens.
- **`get_run_summary` aggregation** (pass rate / flaky / avg duration) — add if reporting agents
  need digests; Phase 3 report logic can be reused then.
- **stdio transport** for the product server — HTTP-only now.
- **Server-side durable task store** — task state derived from existing run rows.
